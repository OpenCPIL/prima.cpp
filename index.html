Inside the PRIMA Hy4 Preview 770B Experiment: How We Ran It Across Two Machines

Two machines in different locations, across separate networks and connected wirelessly, combined 80 GB of VRAM and 64 GB of RAM to run Hy4 preview 770B at 1.5 TPS.

The Hy4 preview 770B case study explains why we combined existing devices and what the experiment revealed about scalable local AI. The procedure below records the two-rank path used on this testbed.

Remark: We recommend using an AI tool to help deploy this preview. We will simplify deployment in future releases and provide one-click deployment and installation tools.

The deployment in one view

The experiment was a two-rank static topology. The four-A4000 machine was rank 0 and exposed the client API. The 4090 Laptop was rank 1 and joined as the second worker.

The single file is 229,412,839,872 bytes. Put one assumed-complete, fixed copy on fast local storage on each machine. Each wrapper opens the local file on FD 203, and --model reads it through /proc/self/fd/203.

The cross-LAN link carried intermediate activations and control traffic, not a continuous stream of 200GB-plus model weights.

The model is assumed complete and fixed. If it is moved or replaced, create a fresh private state directory and new receipt rather than reusing the old binding.

The command options have the following roles:

  • create-v1 reads the supplied manifest and creates a version-1, machine-local artifact receipt; it does not create the manifest;
  • --adapter-id selects PRIMA’s model-specific STQ1_0 adapter;
  • --repository and --revision pin the model’s source and immutable repository revision;
  • --manifest points to the fixed local JSON containing the declared filename, byte size, and artifact provenance; it does not request a local payload hash;
  • --model-root points to the local directory containing the GGUF;
  • --output writes the receipt that this machine passes to prima-server at startup.

Generate the receipt once on each machine and reuse it only while the model file and its absolute local path remain unchanged. Authority paths must be canonical absolute paths with no symlink component; every input must be owned by the effective user, be a regular file with link count one and exact mode 0600; the output parent must be owned by that user with exact mode 0700. chmod alone cannot repair a wrong owner, hard link, or symlink.

The clean env -i probe deliberately matches the launch’s PCI-bus CUDA ordering and leaves GGML_CUDA_P2P unset; either setting can change the topology digest and make manual startup reject the plan. A plain redirection under the common 022 umask creates mode 0644, which the authority checks also reject. Keep each topology, receipt, plan, profile-cache path, and their parent state directory private.

5. Generate the hybrid two-rank placement plan

This testbed combined two levels of parallelism. Across the approximately 50 ms cross-LAN link, the two ranks used layer/pipeline partitioning. Inside the four-A4000 rank, PRIMA used local expert parallelism for routed MoE work. The manual plan establishes the inter-rank cut and assigns each layer’s resident main-graph tensors, shared-expert weights, state, and KV cache to a reference GPU. Routed-expert banks are managed separately by the tiered MoE runtime.

For this preview, the reference placement was selected explicitly and then validated and materialized with prima-moe-plan. Copy rank 1’s receipt and topology file to rank 0 over an authenticated channel, place them inside rank 0’s private STATE, and force mode 0600. Use absolute paths and a fresh, absent output path:

--cut 61 assigns model layers 0–60 to rank 0 and layers 61–77 to rank 1. The per-device counts are contiguous base layer placement and expand as follows:

Rank 0CUDA3 · A40001645–60

This table is layer placement, not expert parallelism. For each contiguous range, the listed GPU owns the resident main graph—including attention, routing, and normalization tensors—the shared-expert weights, and that layer’s state and KV cache. The counts do not divide the routed-expert bank among GPUs.

Expert parallelism is a second, intra-rank step that applies only to routed experts. For routed MoE layers 1–60 on rank 0, accepted hot-expert weights are striped across all four A4000 GPUs using (reference owner + expert ID mod 4) mod 4. For example, if CUDA1 is the reference owner, expert IDs 0, 4, … prefer CUDA1; 1, 5, … prefer CUDA2; 2, 6, … prefer CUDA3; and 3, 7, … prefer CUDA0, subject to hot-cache capacity. Independent GPU expert branches are submitted together, overlap with the local CPU cold-expert branch backed by host memory and SSD, and are then reduced in a stable order.

Rank 1 has one GPU, so it has no intra-rank multi-GPU expert fan-out. PRIMA does not fan experts across the two machines: doing so would introduce expert communication at every routed layer over the high-RTT cross-LAN path.

The tool does not search for the fastest placement. It verifies that the two receipts refer to the same model artifact and adapter, checks both captured GPU topologies, validates the selected cut and layer counts, and writes a binary plan. These values describe this testbed and should not be copied to different hardware without a new placement decision. Transfer the generated plan without modifying it; on rank 1, receive it outside STATE, require the destination to be absent, then run install -m 600 /absolute/path/to/received-plan "$STATE/hy4-two-rank-plan.prmp". Both ranks pass their private local copy through --moe-manual-plan.

6. Start rank 0 and rank 1

The two processes connect with a data port and a signal port on each rank. The tested path uses an SSH tunnel because direct reverse reachability was unavailable. Start the tunnel, then rank 1 with --worker-ready-listener, and finally rank 0 as --head --world 2.

Secure the ports before starting anything. In this preview, the Ring data/signal and diagnostic echo listeners bind wildcard interfaces, and the reproduced rank 0 HTTP listener appeared on 0.0.0.0:18331 even with --host 127.0.0.1. These listeners have no TLS or client authentication. Use site-specific firewall and routing rules to deny untrusted ingress to 18331, 18332, 19540, 19541, 20570, 20571, 20770, and 20771 while preserving required loopback traffic. Inspect ss -ltnp on both hosts before launch to confirm all declared and forwarded ports are free. Do not paste generic firewall commands that could cut off SSH.

Before first use, verify the A4000 host-key fingerprint through a separate trusted channel and record it in known_hosts; do not blindly accept a TOFU prompt. In Terminal A on the Laptop, keep this tunnel in the foreground. 7. The settings that shaped the run

The essential settings were:

  • /proc/self/fd/200, /proc/self/fd/201, and /proc/self/fd/203: consume the receipt, manual plan, and model through the descriptors pinned by the wrapper, rather than reopening mutable pathnames inside the server;
  • --topology static, --world-timeout 7200, and --moe-hybrid manual: satisfy the current STQ startup contract by selecting the declared static two-rank topology, allowing up to 7,200 seconds for rank coordination and cold startup, and requiring the supplied manual hybrid-MoE plan;
  • --moe-provider tiered-local-cold-hot-v1: keep hot expert data on GPU while using host memory and local SSD for colder data;
  • --moe-routing-policy local-cold-no-remote-v1: read a rank’s cold weights locally instead of fetching them from the other machine;
  • --moe-manual-plan /proc/self/fd/201: load the same validated plan on both ranks through required FD 201; a normal filesystem path is rejected by the current manual-mode contract;
  • --load-mode mmap: map the 229 GB model and allow colder pages to be served from each rank’s local storage;
  • --split-mode layer: place resident main-graph and shared-expert layer data according to the plan; routed hot experts still use rank 0’s local expert parallelism;
  • --moe-device-group: declare the ordered local GPU group available to each rank;
  • --ctx-size 8192 --batch-size 2 --ubatch-size 1 --parallel 1: run one request at a time with the measured 8K-context batch configuration;
  • --no-warmup --no-repack: skip automatic warmup and weight repacking for this recorded path;
  • --jinja: apply the model’s Jinja chat template so /v1/chat/completions has reliable chat semantics.

The common wrapper also fixes PCI-bus GPU ordering, disables CUDA graphs, enables the measured CPU–CUDA numeric-compatibility path, and sends inter-rank activations as FP32. The PRIMA_MOE_* variables shown in the common block explicitly enable the reproduced request planner, hot-cache policy, cold prefetch, page-cache population, background staging and promotion, and asynchronous copy synchronization. Omitting them is a different, unverified configuration.

We replay the measured generation in the Playground. The Playground does not connect to live devices or start a live inference run; it replays the fixed input, output, and per-token timing captured from a real offline inference run.

专家并行是随后发生在 rank 内部、仅作用于 routed experts 的第二步。对 rank 0 的路由 MoE 层 1–60，被接纳的 hot-expert weights 会按照 (参考 owner + expert ID mod 4) mod 4 分散到四张 A4000。例如，参考 owner 为 CUDA1 时，expert ID 0、4、……优先进入 CUDA1；1、5、……进入 CUDA2；2、6、……进入 CUDA3；3、7、……进入 CUDA0，实际放置还需满足 hot cache 容量。多个 GPU expert branches 会一起提交，与由本机主存和 SSD 支撑的 CPU cold-expert branch 重叠执行，最后按稳定顺序归并。

Rank 1 只有一张 GPU，因此没有 rank 内多 GPU expert fan-out。PRIMA 不在两台机器之间做专家分发，因为这会让每个路由层都经过高 RTT 的跨 LAN 链路交换专家数据。

这个工具不会自动搜索最快的放置方案。它会确认两个凭据指向同一模型制品和适配器，检查两端记录的 GPU 拓扑，验证人工选择的切分点与各 GPU 层数，并写出二进制 plan。这些参数只对应本测试环境，硬件变化后需要重新决定放置方式。原样传输生成的 plan；在 rank 1 上先接收到 STATE 之外，确认目标不存在，再执行 install -m 600 /absolute/path/to/received-plan "$STATE/hy4-two-rank-plan.prmp"。两个 rank 启动时都通过 --moe-manual-plan 使用各自的私有本地副本。

关键设置包括：

  • /proc/self/fd/200、/proc/self/fd/201 和 /proc/self/fd/203：通过 wrapper 固定的描述符读取 receipt、manual plan 和模型，避免服务端再次按可变路径名打开这些文件；
  • --topology static、--world-timeout 7200 和 --moe-hybrid manual：满足当前 STQ 启动合同，使用声明的双 rank 静态拓扑，为 rank 协调和冷启动预留最多 7,200 秒，并要求使用提供的手动 hybrid-MoE plan；
  • --moe-provider tiered-local-cold-hot-v1：热专家数据保留在 GPU，较冷的数据使用主机内存和本地 SSD；
  • --moe-routing-policy local-cold-no-remote-v1：每个 rank 从本地读取自己的冷权重，而不是从另一台机器获取；
  • --moe-manual-plan /proc/self/fd/201：两个 rank 都通过必需的 FD 201 加载同一份经过校验的 plan；当前 manual-mode 合同会拒绝普通文件系统路径；
  • --load-mode mmap：映射 229 GB 模型，让较冷的页面由每个 rank 的本地存储提供；
  • --split-mode layer：按 plan 放置常驻 main-graph 和 shared-expert 层数据；routed hot experts 仍使用 rank 0 内部的本地专家并行；
  • --moe-device-group：声明每个 rank 可用且有序的本地 GPU 组；
  • --ctx-size 8192 --batch-size 2 --ubatch-size 1 --parallel 1：以本次实测使用的 8K 上下文 batch 配置，每次运行一个请求；
  • --no-warmup --no-repack：在这条记录路径中跳过自动 warmup 和权重 repack；
  • --jinja：应用模型的 Jinja chat template，确保 /v1/chat/completions 具有可靠的聊天语义。

公共 wrapper 还会固定 PCI 总线 GPU 顺序、关闭 CUDA graphs、启用实测的 CPU–CUDA 数值兼容路径，并以 FP32 传输 rank 间激活。公共代码块中列出的 PRIMA_MOE_* 变量明确启用本次复现所用的 request planner、hot-cache policy、cold prefetch、page-cache population、后台 staging/promotion 与异步 copy synchronization；省略它们就属于未经验证的另一套配置。

Scalability Matters More Than a Bigger Machine: What PRIMA’s Hy4 Preview 770B Experiment Reveals About Local AI

PRIMA is not trying to make one ordinary machine perform a miracle. It lets the devices we already own work together and push the boundaries of local AI further.

Every local AI performance number hides a trade-off

Life is full of trade-offs. Local AI is no different.

We have already seen remarkable local AI throughput. With a highly customized hardware setup, for example, two RTX 2080 Ti cards modified to 22GB of VRAM and connected over NVLink can deliver more than 100 TPS for single-request generation with Qwen 3.8 27B.

FreeToken, as another example, has accelerated GLM-5.2 753B to 15 TPS on an RTX PRO 6000 96GB, but that setup requires 512GB of host memory.

Other approaches use low-bit quantization to bring interactive throughput for hundred-billion-parameter MoE models to consumer workstations.

All of these approaches are valuable, but each encodes a different trade-off among intelligence, speed, and cost:

  • Larger models, and models closer to full precision, come with a sharp loss in speed;
  • Lowering quantization precision can reduce model capability;
  • Custom or more powerful CPUs and GPUs, more system memory, and greater memory bandwidth raise hardware cost;
  • Laptops we already own often have limited RAM and VRAM, forcing us toward smaller models or lower precision.

These are impressive systems. But:

Choosing a fixed hardware configuration also means choosing its ceiling. If frontier models grow, the machine quickly becomes insufficient. If frontier models shrink, we may have bought more than we need. Either way, an expensive fixed configuration can easily become a sunk or unnecessary cost.

This does not mean we should never buy stronger hardware. The problem is that local AI requirements change quickly, while hardware remains fixed.

A high-memory workstation purchased today for a 100B model may be insufficient tomorrow when the model grows to 700B. We then look for another, stronger machine: new GPUs, more and larger memory modules, a faster CPU and SSD, perhaps even a new motherboard, power supply, cooling system, and chassis. Meanwhile, the hardware we already paid for becomes a sleeping asset.

The reverse can also happen. If MoE, sparsity, or a more efficient architecture produces a stronger model with fewer parameters, the expensive hardware purchased specifically for a “large model” may be wasted.

That led us to a different question:

Instead of repeatedly searching for a new machine that only meets today’s requirements, can the machines we already own keep scaling as those requirements change?

PRIMA pursues scalability, not a “speed miracle”

PRIMA is not designed to set a local AI throughput record on one carefully selected hardware configuration. It focuses on a different and more common real-world situation.

We may already have a laptop, an older workstation, a Mac Mini, a GPU server at the office, or even devices at a neighbor’s or friend’s home on another LAN. None is powerful enough on its own. But what if we combine them?

PRIMA aims to organize these otherwise independent devices into a local AI cluster that can expand on demand. It wakes sleeping assets and lets every machine contribute whatever remains useful. As new devices join, the capacity of the cluster can continue to grow.

PRIMA does not optimize only for “fastest.” It expands four boundaries of local AI as needed: larger models, faster generation, longer context, and higher model precision. In other words:

Do not buy an entirely new machine every time requirements grow. Add devices to the local AI cluster when demand rises, and release them when demand falls. Those devices are ones we already own.

This is what PRIMA means by scalable local AI.

Hy4 preview 770B gave us an extreme experiment

When Tencent released Hy4 preview, we saw a model that was unusually well suited to testing this idea.

Hy4 preview is a 770B-parameter MoE model. Its MoE layers contain 256 routed experts and one shared expert. For every generated token, eight routed experts plus the shared expert are activated, for roughly 49B active parameters per token.

The MoE architecture does not activate all 770B parameters for every token, but the complete expert weights still place enormous pressure on RAM and VRAM. Even after aggressive 1-bit quantization, storing the Hy4 preview 770B parameters requires more than 200GB. That pushed our question to an extreme:

Without buying any new hardware for Hy4 preview, how far could I run this 770B model using only the devices already available to me?

My first device was the laptop I use every day:

At that point, I might as well call the result a high-memory workstation.

I did not want to build or buy an expensive high-memory workstation for one model. Apart from electricity, my hardware budget was zero.

Instead, I used llama.cpp with mmap and disk streaming to run Hy4 preview 770B IQ1 directly on the laptop.

The model ran. But its per-token latency reached 5.9 s/token, or approximately 0.17 TPS.

From the narrow perspective of whether the model could start, this was a success. In practice, it was painfully slow. About 0.17 TPS was the laptop’s single-device limit under this model and quantization, before introducing accelerators such as MTP, DFlash2, or DSpark.

Using PRIMA to combine two insufficient machines

If we simply add the system memory and VRAM of the two devices, we get:

  • Laptop: 32GB RAM + 16GB VRAM;
  • GPU server: 32GB RAM + 64GB VRAM;
  • Total: 144GB of combined RAM and VRAM.

That is still smaller than the model file itself, and those resources are scattered across two machines, five GPUs, multiple PCIe links, and different storage devices.

The machines are not even on the same LAN. The laptop reaches the GPU server on a remote LAN over Wi-Fi and a VPN. Network RTT is approximately 50ms; the laptop’s downlink is only 145 Mbps, and its uplink is lower still at 27 Mbps.

From an HPC perspective, this is almost exactly the kind of hardware and network setup one would be told not to use for distributed large-model inference. Yet it reflects the real world of local AI: heterogeneous devices, limited memory, and wireless networking.

PRIMA did not try to squeeze more than 200GB of model weights into 144GB of aggregate memory. Instead, it used a layered, distributed execution strategy:

  • Run some MoE layers on the 4090 Laptop;
  • Assign most MoE layers to the four-A4000 server;
  • Keep frequently used hot experts on the GPUs;
  • Leave temporarily inactive cold experts in host memory or on SSD;
  • Learn dynamically which experts are worth caching from the routing observed in the current request;
  • Prefetch experts that the next stage is likely to use from SSD;
  • Overlap disk reads, GPU computation, and network communication wherever possible;
  • Execute experts in parallel within each node, distributing expert work across multiple GPUs;
  • Reduce unnecessary data copies and repeated loading;
  • Transmit only intermediate activations and control messages between devices, not enormous expert weights.

Think of the system as an enormous tool warehouse. Hy4 preview has hundreds of tools, but a specific problem needs only a few of them at a time. The GPU is a fast workbench close to the worker, but it has little space. The SSD is a vast warehouse, but retrieving a tool takes time. PRIMA tries to predict which tools will be needed next, move them close to the workbench in advance, and keep multiple workers and warehouses busy at the same time.

From 6 seconds to 1.5 TPS

With PRIMA coordinating the two devices, we measured:

ConfigurationThroughput

4× A4000 Server + llama.cpp0.37 TPS
4090 Laptop + 4× A4000 + PRIMA1.5 TPS

With the two devices working together, throughput increased by 8.8× over the laptop alone and by 4.1× over the four-A4000 server alone.

1.5 TPS is not a speed worth boasting about. What matters is this:

Without spending anything on new hardware, we accelerated a 770B model by 8.8×.

1.5 TPS is nowhere near PRIMA’s performance ceiling

More importantly, the primary bottleneck in this two-machine system is still not CPU or GPU compute. It is streaming model data from SSD. The complete Hy4 preview IQ1 weights remain larger than the RAM and VRAM that can stay resident across both devices. Every generated token still requires substantial cold-expert data to be read from SSD. Prefetching, the page cache, expert caching, and computation overlap hide as much disk latency as possible, but SSD bandwidth remains the clearest bottleneck.

Therefore:

1.5 TPS is the limit of these two devices, not the performance limit of PRIMA.

Replacing the SSDs with higher-throughput storage in the future would leave significant room for improvement.

Adding another device—a neighbor’s desktop or a colleague’s Mac Mini—could also create meaningful headroom.

A new device contributes more than CPU or GPU compute. It also adds system memory, GPU memory, and parallel SSD bandwidth.

The model can be distributed further, each machine can read fewer weights from disk, and multiple SSDs can operate simultaneously. Eventually, the bottleneck will move from storage to compute or networking.

Only as requirements continue to grow do we need to introduce more advanced compute, high-speed wired interconnects, optical wireless links, or other advanced technologies into the local cluster.

This is the point of a scalable system:

Do not begin by paying for maximum performance. Begin with the requirements of the application, identify the current bottleneck, and expand only the resource that limits it.

PRIMA complements single-device techniques

PRIMA’s emphasis on scalability is what most clearly distinguishes it from many high-performance local AI approaches.

PRIMA does not reject better GPUs, more powerful AI chips such as Xring, larger memory, faster SSDs, or better quantization. Nor does it compete with FreeToken, llama.cpp, or future single-machine optimizations.

On the contrary:

The stronger each machine becomes, the stronger the foundation of a PRIMA cluster becomes.

If an exceptionally powerful local AI inference machine appears in the future, PRIMA can make it the origin of the cluster. The 4090 Laptop, A4000 Server, and other devices we already own can remain expansion nodes.

If models keep growing, we add more devices around that AI machine.

If context keeps growing, or if we want to move from IQ1 to a higher-precision quantization, the 4090 and four-A4000 server can expand the system RAM and GPU memory available to the AI machine. We do not need to discard it and pay the full cost of an even stronger replacement.

If smaller, more capable models arrive, the PRIMA cluster can scale down at any time and release our laptops and desktops. After all, local AI was not the only reason we bought them.

When we need a 1M-token context, even longer context, or greater concurrency, we can wake those devices again.

From “Can this device run it?” to “What can it contribute?”

PRIMA is making the question “Which AI computer should I buy next?” less important.

When evaluating local AI hardware, we have traditionally asked: “Can this device still run the model?” If the answer is no, a machine with a high sunk cost is put aside.

PRIMA reframes the question: What can this device still contribute to my AI? It may not run Hy4 preview alone, but it has a GPU. The GPU may not be fast, but it has 16GB of VRAM and the machine has 32GB of RAM. The CPU may be old, but the device has a fast NVMe SSD. None of it may be flagship hardware, yet several such devices together can support something no single one of them can do.

For personal and home AI, this matters more than chasing the highest TPS in a single benchmark. Because:

Real-world user-side computing resources are heterogeneous, and they already surround us. What local AI lacks is the ability to unify those heterogeneous resources.

The system may be slow, but slow systems still have useful applications, and we can add capacity to make them faster.

The model may be less capable, but most real-world tasks do not require the most capable model. We can add capacity until it becomes capable enough.

PRIMA + Hy4 preview 770B was a successful stress test. It did not create a local AI throughput miracle. It showed that 0.37 TPS on one device was not the limit of what I could deploy without new hardware, and that 1.5 TPS across two devices is not the end of the performance curve.

Where will that boundary move when the next device joins?

That is the question PRIMA intends to keep answering.

不可忽视的可扩展性：PRIMA 的 Hy4 Preview 770B 压测揭示本地 AI 新方向

PRIMA 不追求单机奇迹，而是让已有设备一起，把本地 AI 的边界推得更远。

本地 AI 的每一个性能数字背后，都有取舍

人生处处是取舍，本地 AI 也是如此。

今天，我们已经看到许多令人惊叹的本地 AI 吞吐。例如，在定制的硬件条件下，两张改装到 22GB 显存、通过 NVLink 互联的 RTX 2080 Ti，可以让 Qwen 3.8 27B 实现超过 100 TPS 的单请求生成速度。

又例如， FreeToken 在 RTX PRO 6000 96GB 上将 GLM-5.2 753B 加速到 15 TPS，但要求 512 GB 主机内存。

另一些方案通过低比特量化、让上百 B 的 MoE 模型在消费级工作站上达到可交互的吞吐。

这些方案都很有价值，但它们隐含着不同的“智能-速度-成本”的取舍：

  • 更大的模型、越接近满血，背后是速度的显著下降；
  • 调低量化精度，隐含着模型能力损失；
  • 换上定制/更强的 CPU 和 GPU，更大的系统内存、显存带宽，隐含着更高的硬件成本。
  • 已经购买的笔记本电脑，显存小，主存也小，只能降级到更小模型或更低精度。

这些方案很出色，但：

选择特定硬件，也就选择了它的上限：SOTA 模型变大，它很快不够用；SOTA 模型变小，它又可能买多了。最终，昂贵的固定配置很容易变成沉没成本/不必要成本。

这并不是说我们不应该购买更强的硬件。问题在于，本地 AI 的需求变化得太快，而硬件是固定的。

今天为了某个 100B 模型购买的大内存工作站，明天可能因为模型增长到 700B 而再次不够。于是，我们继续寻求一台更强的整机，购买新的 GPU、更多/更大的内存卡、更强的 CPU、更快的 SSD，甚至新的主板、电源、散热系统和机箱。与此同时，之前已经购买的设备将变成沉睡资产。

反过来，如果新的模型通过 MoE、稀疏化或更高效的架构，在更小参数量下获得了更强能力，那么今天为了“大模型”额外购买的高昂硬件，又会被浪费。

所以，我们开始思考另一个问题：

与其不断寻找一台仅能满足当前需求的新机器，能否让我们已经拥有的机器随需求的变化持续扩展？

PRIMA 追求的不是“速度奇迹”，而是可扩展性

PRIMA 的目标不是在某一套精心选择的硬件上刷新本地 AI 的吞吐纪录。它更关注现实世界中的另一种情况：

我们已经有一台笔记本，也许还有一台旧工作站、一台 Mac Mini、一台办公室里的 GPU 服务器，甚至几台邻居或朋友家里、不同局域网中的设备。它们单独看，都不够强。但它们加在一起呢？

PRIMA 希望把这些原本彼此独立的设备组织成一个可以按需扩展的本地 AI 集群，唤醒沉睡资产，让每一台设备贡献自己仍然有价值的部分。当新的设备加入时，整个集群的容量可以持续增长。

PRIMA 所追求的不是“最快”， 而是按需扩展本地 AI 的四个边界： 更大的模型、更快的生成速度、更长的上下文，或更高的模型精度。换句话说：

不是每次需求增长都重新买一台机器。当需求增长时，我们往本地 AI 集群增加新设备；当需求削减时，我们从本地 AI 集群撤出设备。而这些设备，是我们已经购买的。

这也是 PRIMA 所关注的“可扩展本地 AI”。

当 Hy4 preview 770B 发布，我们想做一个极端实验

在腾讯发布 Hy4 preview 后，我们看到了一个非常适合验证这个想法的模型。

Hy4 preview 是一个 770B 参数规模的超大 MoE 模型，它的 MoE 层包含 256 个路由专家和 1 个共享专家，每生成一个 token，会激活其中 8 个路由专家和共享专家。模型每个 token 的激活参数约为 49B。

虽然 MoE 架构并不会在每个 token 上激活全部 770B 参数，但完整的专家权重仍然给主存和显存带来巨大压力。即使经过激进的 1-bit 量化， Hy4 preview 770B 的模型参数存储需求仍然高达 200 GB+，这把我们的问题推到一个极端规模：

如果不为了 Hy4 preview 购买任何新硬件，仅凭我手上的现有设备，能把这个 770B 模型跑到什么程度？

第一台设备：一台普通的 4090 Laptop

我手里的第一台设备，是一台日常使用的笔记本电脑：

而我并不想为了一个模型，大价钱打造/重新买一台大内存工作站。除了电费，我一分钱预算都没有。

用 PRIMA 把两台不够用的机器拼在一起

把两台设备的系统内存和显存简单相加，我们获得了：

  • 笔记本：32GB RAM + 16GB VRAM；
  • GPU 服务器：32GB RAM + 64GB VRAM；
  • 合计：144GB RAM + VRAM 容量。

这仍然小于模型文件本身，而且这些资源分散在两台机器、五张 GPU、多个 PCIe 链路和不同的存储设备上。

它们甚至不在同一个局域网里：笔记本通过 Wi-Fi 和 VPN 访问远端局域网中的 GPU 服务器，网络 RTT 约为 50ms，笔记本的下行带宽仅为 145 Mbps，上行带宽更低，仅为 27 Mbps。

从 HPC 的角度看，这几乎是一套“不应该拿来做分布式大模型推理”的硬件和网络设施。但这正是本地 AI 面对的真实世界：异构设备、小内存、无线网络。

PRIMA 没有尝试把超过 200GB 的模型权重全部塞入 144GB 的聚合内存。它采取的是一种分层、分布式的执行方式：

  • 将一部分 MoE 层放在 4090 Laptop 上运行；
  • 将大部分 MoE 层分配给四卡 A4000 服务器；
  • 把高频使用的热专家保留在 GPU；
  • 把暂时不活跃的冷专家留在主机内存或 SSD；
  • 根据当前请求实际发生的专家路由，动态学习哪些专家值得缓存；
  • 提前从 SSD 预取下一阶段可能使用的专家；
  • 让磁盘读取、GPU 计算、网络通信尽可能重叠；
  • 单机内专家并行，将多个专家任务分散到多张 GPU 上并行执行；
  • 减少不必要的数据复制和重复加载；
  • 设备之间只传中间激活和控制信息，不传庞大的专家权重。

可以把它理解成一个非常大的工具仓库。 Hy4 preview 有几百种工具，但解决一个具体问题时，一次只需要其中少数几种。 GPU 是离工人最近的工作台，但空间很小。 SSD 是巨大的仓库，但取工具比较慢。 PRIMA 要做的事情，就是尽可能预测“接下来最可能用什么工具”，提前把它们放到工作台附近，同时让多个工人、多个仓库一起工作。

1.5 TPS 不是一个值得炫耀的速度。真正重要的是：

我们没有付出任何成本，就把一个 770B 模型加速 8.8 倍。

1.5 TPS 远不是 PRIMA 的性能上限

更重要的是， 目前这套两机系统的主要瓶颈依然不是 CPU/GPU 算力，而是 SSD 的磁盘流式读取。因为 Hy4 preview IQ1 的完整模型权重仍然大于两台设备能够常驻的内存和显存， 每生成一个 token，仍然有大量冷专家权重需要从 SSD 中读取。即使我们已经通过预取、page cache、专家缓存和计算重叠尽量隐藏磁盘延迟，SSD 带宽依然是当前系统最明显的瓶颈。

因此：

1.5 TPS 只是这两台设备的极限，并不是 PRIMA 的性能极限。

如果我们把 SSD 换成未来吞吐更高的存储，性能仍有显著提高空间。

如果我们再加入一台设备， 比如邻居家的台式机、工位旁朋友的 Mac Mini，同样有显著提高空间。

因为新设备带来的不仅是 CPU/GPU 算力，它同时增加：系统内存、GPU 显存、SSD 并行带宽。

模型可以被进一步分散，每台机器需要从磁盘读取的权重变少，多个 SSD 可以同时读取。最终，瓶颈将从磁盘转移到算力或网络。

随着需求进一步提高，我们才需要考虑向本地集群中引入更先进的算力，或有线高速互联，或无线光通信等更先进技术。

这正是可扩展系统的意义：

不是一开始就追求高成本的极致性能，而是以满足应用实际需求为目标，定位当前瓶颈，再只扩容对应的资源。

PRIMA 与高性能单机技术并不矛盾

PRIMA 关注可扩展，这是它与很多本地 AI 高性能方案最大的不同。

PRIMA 不排斥更好的 GPU、更强力的 AI 芯片（如玄戒）、更大的内存、更快的 SSD、更好的量化方法，也不排斥 FreeToken、llama.cpp 或未来更先进的单机优化技术。

恰恰相反：

单机能力越强，PRIMA 集群的基础能力就越强。

如果未来出现一台性能极强的本地 AI 推理机，PRIMA 将把它作为集群原点，而我们原来的 4090 Laptop、A4000 Server 或其他设备仍然可以作为扩容节点。

模型继续变大，我们以 AI 推理机为原点，继续增加设备。

上下文继续变长，或希望从 IQ1 提高到更高量化精度，我们用 4090、四卡 A4000 Server 为 AI 推理机扩充系统主存和 GPU 显存。不需要丢弃原推理机，为更强推理机重新支付高昂费用。

如果未来出现了更小、更强的模型，PRIMA 集群可以随时缩容，解放我们的笔记本和台式机，毕竟这些设备也不是为了本地 AI 而购买的。

当我们需要 1M 甚至更长上下文、更高并发时，又可以再次唤醒这些设备。

从“这台设备能不能跑”到“这台设备能贡献什么”

PRIMA 正在让“未来最值得买哪一台 AI 电脑？”变得没那么重要。

过去，我们评估本地 AI 硬件时，经常问：“这台设备还能不能跑这个模型？” 如果不能，这台已经支付了高沉没成本的机器将被尘封。

PRIMA 旨在把这个问题换成：这台设备还能为我的 AI 提供什么？ 也许它无法独立运行 Hy4 preview， 但它有一张 GPU；也许 GPU 不强，但它有 16GB 显存和 32GB 内存； 也许 CPU 很旧，但它有一块高速 NVMe SSD。也许它什么都不是旗舰，但几台这样的设备放在一起，就可能支撑一件任何单台设备都做不到的事情。

对于家庭和个人 AI 来说，这比追求某一次 benchmark 中的极限 TPS 更重要。因为：

现实世界中的用户侧计算资源，本来就是异构的， 而且它们已经在我们身边。本地 AI 缺少的，只是整合这些异构资源的能力。

它可能很慢，但慢有慢的应用场景，我们可以通过扩容尽量提速它。

它可能不聪明，但现实世界大部分真实任务，其实不需要那么聪明，我们通过扩容把它变得更聪明，就足够了。

PRIMA + Hy4 preview 770B 是一次成功的压力测试，它没有创造本地 AI 吞吐的奇迹，但它证明了单设备 0.37 TPS 不是我零成本部署的极限，而两设备 1.5 TPS 也不是性能的终点。

那么，下一台设备加入之后，这个边界会在哪里？

这正是 PRIMA 接下来想继续回答的问题。
